# HiDock Next 2.0 UI 日本語化 設計書

- 作成日: 2026-09-22
- 対象リポジトリ: `sgeraldes/hidock-next-2`（クローン元 HEAD `95908f2`）
- 作業ブランチ: `feat/i18n-ja`
- 方式: react-i18next による i18n 基盤の導入（英語を残したうえで en / ja を切り替える）

## 1. 背景と目的

HiDock Next 2.0 は Electron + React + TypeScript で書かれた、HiDock レコーダー向けのローカルファーストな知識ワークスペースである。UI は全面的に英語で、i18n の仕組みは一切入っていない。

- `i18next` などの国際化ライブラリへの依存なし
- ロケールファイルなし
- 設定画面に言語の項目なし
- 英語の文字列はすべて TSX に直接書かれている

なお `AppConfig.transcription.language` と `UnifiedRecording.language` は既に存在するが、これらは**文字起こしの言語**を指すフィールドであり、UI の表示言語とは無関係である。

本設計の目的は、UI の表示言語を日本語に切り替えられるようにすることである。翻訳対象は画面に出る文言（ラベル、ボタン、見出し、プレースホルダ、ツールチップ、トースト、エラーメッセージ）に限る。

## 3. i18n 基盤

### 3.1 依存関係

追加するのは次の 2 つのみ。

- `i18next`
- `react-i18next`

react-intl や LinguiJS ではなく i18next を選ぶ理由は 3 つある。

1. 既存コードに `meeting{count === 1 ? '' : 's'}` 形式の英語の複数形が散在しており、複数形ルールを持つライブラリが必要である
2. `<code>` や `<strong>` を文中に含む JSX が実在する（例: `pages/Settings.tsx:960`）。`<Trans>` コンポーネントがないと、こうした文をキー 1 個に保てない
3. デファクトスタンダードであるため、上流に還元しやすい

### 3.2 ディレクトリ構成

```
apps/electron/src/i18n/
  index.ts                    i18next の初期化
  locales/en/common.json
  locales/en/layout.json
  locales/en/library.json
  locales/en/device.json
  locales/en/settings.json
  locales/en/today.json
  locales/ja/(同じ 6 ファイル)
```

ネームスペースは機能単位で切る。これは既存の `lazyWithRetry` によるページ単位のコード分割、および `electron.vite.config.ts` の `manualChunks` の区切りと一致する。

`common` だけは例外で、機能に属さない共通の語を置く。具体的には汎用のボタン（保存 / キャンセル / 閉じる / 削除 / 再試行）、共通の状態語（読み込み中 / エラー / 空）、および `smartDate.ts` が使う日付のフォールバック文言である。2.1 節の表に `common` の行がないのは、この 6 つ目のネームスペースが特定の画面に紐づかず、対象 77 ファイルから重複した語を集約して作るものだからである。文字列数は集約の結果として決まるため、事前には見積もらない。

### 3.3 キーの命名規則

`<namespace>:<component>.<slug>` の形をとる。

- `library:filters.statusAll`
- `device:connect.button`
- `settings:language.label`

### 3.4 初期化の設定

- `fallbackLng: 'en'`
- `interpolation.escapeValue: false`（React が自前でエスケープするため）
- 開発ビルドのみ `missingKeyHandler` で未訳キーを警告する。本番ビルドでは静かに英語へフォールバックする

### 3.5 複数形

既存の `meeting{count === 1 ? '' : 's'}` 形式を `t('library:meetings', { count })` に畳む。カタログ側は次のようになる。

```json
// en
{ "meetings_one": "{{count}} meeting", "meetings_other": "{{count}} meetings" }
// ja
{ "meetings_other": "{{count}}件の会議" }
```

CLDR において日本語の複数形カテゴリは `other` のみであるため、ja 側は 1 形で足りる。

### 3.6 JSX の埋め込み

文中にマークアップを含む箇所は `<Trans>` を使い、キーを 1 個に保つ。文を分割して `t()` を並べると、日本語では語順が変わって破綻するため、この方針を守る。

## 4. 言語の決定と切り替え

### 4.1 設定項目

`AppConfig.ui` に既存の `theme` と並べて `language` を追加する。

```ts
ui: {
  theme: 'light' | 'dark' | 'system'
  language: 'system' | 'en' | 'ja'   // 追加
  defaultView: 'week' | 'month'
  // ...
}
```

既定値は `'system'` とする。既存の `config.json` に `language` がなくても `'system'` として解決されるため、マイグレーションは不要である。

**既定値を `'ja'` にはしない。** `'system'` にしておけば、日本語環境の Windows では自動的に日本語になり、英語環境では英語のままになる。

### 4.2 OS ロケールの取得

`'system'` の解決には `navigator.language` を使う。値が `ja` で始まれば `ja`、それ以外は `en` とする。

**IPC は追加しない。** 当初は `app:info` ハンドラに `app.getLocale()` を足す案だったが、これでは成立しない。`app:info` は非同期の IPC であり、React のマウント前（プリペイント）には値が返ってこないためである。テーマが `matchMedia` を同期的に読めるのとは事情が異なる。

Electron の renderer における `navigator.language` は Chromium のロケールであり、Electron はこれを `app.getLocale()` と同じソースから設定する。したがって値は一致し、かつ同期的に読める。IPC を足さずに済むぶん、可動部品が減る。

jsdom では `navigator.language` が `'en-US'` を返すため、テスト環境では自然に `en` に解決される。これは 6.1 節の「テストは英語で動かす」方針と整合する。

### 4.3 既存のテーマ機構を写す

テーマの切り替えには、ちらつきを防ぐためのよくできた仕組みが既にある。言語も同じ形に揃える。

| テーマ（既存） | 言語（新規） | 役割 |
| --- | --- | --- |
| `lib/theme.ts` の `bootstrapTheme()` | `lib/language.ts` の `bootstrapLanguage()` | React のマウント前に localStorage から適用する |
| `store/ui/useUIStore.ts` の `theme` | 同ファイルに `language` を追加 | localStorage に永続化する |
| `hooks/useTheme.ts` | `hooks/useLanguage.ts` | 設定との突き合わせと切り替えを担う |
| `config.ui.theme` へミラー | `config.ui.language` へミラー | セッションをまたいで残す |

ストアの追加先は `src/store/ui/useUIStore.ts` である。`src/store/useUIStore.ts` は後方互換のための再エクスポートに過ぎず、ファイル冒頭に「ここで別の `create()` を書くな。両方のパスが同一の Zustand インスタンスに解決されなければならない」という警告がある。この指示に従い、再エクスポート側には手を入れない。

永続化の対象を絞るため、`theme` と同様に `partialize` の対象へ `language` を明示的に加える。

`src/main.tsx` で `bootstrapTheme()` の隣に `bootstrapLanguage()` を呼ぶ。これにより、起動時に英語が一瞬見えてから日本語に切り替わる、という挙動を避けられる。

### 4.4 設定画面

`pages/Settings.tsx` の先頭に `Appearance` という新しい `<Card>` を追加し、その中に言語セレクタを置く。選択肢は「システムに従う / English / 日本語」の 3 つ。

**テーマセレクタの隣に置くことはできない。UI 上にテーマセレクタが存在しないためである。** `useTheme()` は `App.tsx:105` で DOM との整合のために呼ばれているだけで、`setTheme` や `toggleTheme` を呼び出す UI コントロールはコードベースのどこにもない。現状テーマを変更する手段は `config.json` の直接編集か localStorage の書き換えに限られる。言語セレクタは既存の何かに相乗りするのではなく、新規に作る必要がある。

実装は Radix の `Select` ではなく、`pages/Settings.tsx:731-772` の Assistant カードが使っているセグメント化ボタンの形を踏襲する。`role="group"` と `aria-pressed` を持つ `<button>` を `inline-flex rounded-lg border border-input bg-muted/40 p-0.5` で囲む形で、3 択にそのまま使える。設定画面の中で操作方法を統一するため、この既存パターンに合わせる。

なお、テーマ切り替え UI を追加することは本設計の範囲外とする（日本語化とは独立した機能追加であるため）。

## 5. 日付と時刻

`src/lib/smartDate.ts` が日付表示のほぼ唯一の集約点であり、現状は `'en-US'` と英語の文言を直接埋め込んでいる。

```ts
const date = d.toLocaleDateString('en-US', { month: 'short', day: 'numeric', year: 'numeric' })
```

対応は次のとおり。

- `formatSmartDate` にロケールを渡し、`ja` では `2026年9月22日 · 11:14` の形にする
- 相対表記（`'just now'`、`'3 days ago'` など）は `Intl.RelativeTimeFormat` に置き換え、`3日前` のように出す
- フォールバック文言（`'Unknown date'`）もカタログに載せる
- `smartDate.ts` の外に散る `toLocaleDateString` などは全 52 箇所 / 26 ファイルあるが、Phase 1 の対象ファイルに含まれる分のみ着手する
- `date-fns` は renderer では未使用のため、ロケールの追加は不要である

## 6. 文字列移行の手順

これが本設計でもっとも重要な部分である。

既存のテストは `getByText()` / `findByText()` / `queryByText()` で英語の文字列を **814 箇所 / 64 ファイル** にわたって直接アサートしている。この資産を壊さず、逆に安全網として使う。

### 6.1 英語化リファクタと日本語翻訳を分離する

1. **英語カタログは一字一句そのまま抽出する。** 言い回しの改善、表記ゆれの統一、誤字の修正は一切行わない
2. テスト環境では i18next を `lng: 'en'` 固定で初期化する。初期化コードは `src/test/setup.ts` に置く。このファイルは `vitest.config.ts` の 3 つのプロジェクト（`renderer` / `main-db` / `native-binding`）すべてが読み込む
3. 移行後に `npm run test:run` が基準どおりであれば、英語の表示が 1 文字も変わっていないことの証明になる
4. 日本語カタログは、英語カタログが固まってから別のコミットで作る

この分離を守らないと、テストが落ちたときに「翻訳の誤り」なのか「抽出の漏れ」なのかを切り分けられなくなる。

### 6.2 回帰判定の基準

Phase 0 で計測した基準値は次のとおり。

- `npm run typecheck`: 緑（EXIT 0）
- `npm run test:run`: テストファイル 397 個中 395 個成功、テスト 5,625 件中 5,622 件成功

残る 3 件の失敗は、本作業とは無関係な、上流テストのタイムゾーン前提に起因するものである（詳細は 9.4 節）。回帰判定ではこの 3 件を「既知の赤」として除外する。

## 7. テスト

- **既存の 814 アサート** を英語の回帰網として使う（6.1 節）
- **新規** — `lib/language.ts` の解決ロジックの単体テスト。`'system'` から OS ロケールを経て `en` / `ja` に落ちるまでと、未知のロケールが `en` にフォールバックすること。既存の `src/lib/__tests__/theme.test.ts` がちょうど同じ位置づけ（フレームワークに依存しない解決ロジックだけを対象にしたテスト）なので、これを雛形にする
- **新規** — `useLanguage` が選択を `config.ui.language` にミラーすること。`useTheme` にはフック単位のテストが存在しないため、これは対応する既存テストのない新規の 1 本になる
- **新規** — ja のカタログと en のカタログでキー集合が一致することを検証する構造テストを 1 本。キーの欠落と余剰の両方を検出する
- 翻訳済み画面のスナップショットテストは作らない。保守コストに見合わない

## 8. ビルドと配布

Phase 0（2026-09-22 実施）で、ソースからのビルドが成立することを確認済みである。成果物は `apps/electron/dist/hidock-next-2.0.0-setup.exe`（256 MB）。ビルドログに警告およびエラーなし。

### 8.1 セットアップ手順

ルートの `npm run install:app` だけでは不足する。README の「Build from source」の順序に従う必要がある。

```bash
# 1. 共有パッケージを先に入れてビルドする
for package in ai-providers calendar-sync connectors connectors-slack \
               database jensen-protocol knowledge-graph transcription; do
  (cd "packages/$package" && npm ci && npm run build --if-present)
done

# 2. そのあとでアプリ本体
cd apps/electron && npm ci
```

この順序を守らないと、`packages/*` の `prepare` スクリプトが `tsup` を呼んだ時点で「`'tsup'` は認識されていません」と落ちる。各パッケージは自分の devDependencies に `tsup` を持っており、それが入るのは自分自身の `npm ci` のときだからである。

### 8.2 Electron 本体の取得にはプロキシ用の環境変数が要る

Electron のダウンローダ（`@electron/get`）は `HTTP_PROXY` / `HTTPS_PROXY` を読まない。専用の環境変数を設定する必要がある。

```bash
export ELECTRON_GET_USE_PROXY=true
export GLOBAL_AGENT_HTTPS_PROXY=http://127.0.0.1:3129
export GLOBAL_AGENT_HTTP_PROXY=http://127.0.0.1:3129
```

設定を忘れると、`npm ci` 自体は EXIT 0 で終わるにもかかわらず `node_modules/electron/dist/` が生成されない。症状は実行時の `TypeError: fetch failed` として現れる。インストーラは失敗を握り潰すため、npm の終了コードからは気づけない。

復旧は `apps/electron` で次を実行する。

```bash
node node_modules/electron/install.js
```

`npm run build:win` の途中で electron-builder が取得する nsis、7zip、icons-bundle も、同じ環境変数で問題なく通る。

### 8.3 `npm run check:native` は実行しない

この開発機では、このコマンドは**失敗するだけでなく、リポジトリの状態を壊す**。

原因は、同梱の `@electron/node-gyp` 10.2.0 が Visual Studio Build Tools 2026（v18）を認識できないことにある。node-gyp の Visual Studio 検出は VS2017 / 2019 / 2022 までしか探さない。コンパイラ自体は `C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Tools\MSVC\14.50.35717\` に実在し、Windows SDK 10.0.26100.0 も入っているにもかかわらず、「Visual Studio が見つからない」で落ちる。

問題はその失敗の仕方である。`check:native` は `@hidock/database` のリンクを辿って `packages/database/node_modules/better-sqlite3` まで再ビルドしにいき、失敗したあと **そのコピーを消したまま復元しない**。このバイナリは `main-db` の vitest プロジェクトが `src/test/setup-db.ts` の dual-ABI シム経由で読み込むものであり、失われると DB を使うテストが全滅する（実測: テストファイル 88 個が失敗）。

復旧手順は次のとおり。ソースからのコンパイルではなく prebuild の取得になるため、Visual Studio は不要である。

```bash
cd packages/database && npm rebuild better-sqlite3
```

**`npm run build:win` は `check:native` を必要としない。** このコマンドは開発用のゲートであり、ビルド経路には含まれない。したがって、この開発機では単純にスキップしてよい。

## 9. リスクと既知の問題

### 9.1 上流が活発に更新中である

上流リポジトリは本設計の作成当日にも push されている。クローンは浅いまま維持し、Phase 1 が完了するまで rebase しない。

### 9.2 日本語でレイアウトが崩れる可能性

英語の文字幅を前提にした固定幅が存在する可能性がある。Phase 1 の対象画面は実機で目視確認し、崩れた箇所のみ CSS を調整する。事前に全部直そうとはしない。

### 9.3 ビルドの所要時間と容量

`npm run build:win` は数分で完了し、成果物は 256 MB。`node_modules` を含めた作業ディレクトリは数 GB になる。D ドライブに 1 TB の空きがあるため問題ない。

### 9.4 タイムゾーンに起因する既知の 3 件の失敗

上流のテスト 3 件が、UTC を前提とした期待値を持っているため JST 環境で失敗する。`TZ=UTC` を指定して該当 2 ファイルを実行すると 83 件すべて成功することを確認済みである。

- `electron/main/services/__tests__/retrieval-orchestrator.test.ts` — 「先月」の範囲が `2026-06-01` を期待するところ `2026-05-31` になる（1 日のずれ）
- `src/lib/__tests__/calendar-utils.test.ts` — `toISOString()` による日付バケットのキーとローカル時刻の日付が一致しない

本設計の作業とは無関係であり、修正は行わない。回帰判定の際に「既知の赤」として除外する。

## 10. 実装の順序

1. **Phase 1-A: 基盤** — 依存の追加、`src/i18n/` の作成、`src/test/setup.ts` への `lng: 'en'` 初期化の追加、`AppConfig.ui.language` の追加、`app:info` への `locale` 追加、`lib/language.ts`、`hooks/useLanguage.ts`、設定画面の言語セレクタ
2. **Phase 1-B: layout（10 ファイル / 87 文字列）** — 共通レイアウトを英語カタログに移す。基盤が正しく動くかを最小の範囲で確かめる
3. **Phase 1-C: settings・device・today（12 ファイル / 226 文字列）**
4. **Phase 1-D: library（55 ファイル / 403 文字列）** — 最大の塊。さらに細分する
5. **Phase 1-E: 日付と時刻** — `smartDate.ts` のロケール対応
6. **Phase 1-F: 日本語カタログ** — ここまでで英語カタログが固まっているので、翻訳に専念する
7. **Phase 1-G: 実機確認とレイアウト調整**

各フェーズの終わりに `npm run typecheck` と `npm run test:run` を通し、6.2 節の基準からの乖離がないことを確認する。
